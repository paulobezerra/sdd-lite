# PLAN — Scope integrity and execution traceability across SDD stages

**Feature:** [feature.md](feature.md) · **Spec:** [spec.md](spec.md) · **Date:** 2026-10-22 · **Status:** open

**User validation to start Code:** validated. **Statement:** “fechado”. **Name:** Paulo Bezerra · **Date:** 2026-10-22.

## Delivery strategy

Start with the highest-priority Spec decision-quality improvements, which are independently usable in the Spec stage. Then add the durable Code execution record and continuation rules across feature, bug, and Review-correction work. Align Review to consume that record as evidence while preserving its existing audit. Finish by aligning user-facing documentation and project context with the new artifact and rules. Each increment preserves existing stage contracts; no runtime, data, or migration work is involved.

## Tasks

- **T003-01 — Make Spec decisions visibly follow Feature constraints and compare viable options completely.** **Requirements:** S003-07, S003-08, S003-09. **Precondition:** The validated Feature and Spec contract are the decision baseline; current Spec command, guideline, and template contain the existing option and matrix process. **Scope:** Update `skills/sdd-lite/commands/spec.md`, `skills/sdd-lite/guidelines/specification.md`, and `skills/sdd-lite/templates/spec.md`; align README/docs only if their descriptions of Spec decisions or delivery require it. Require extraction of Feature outcomes, boundaries, hard constraints, priorities, and explicit preferences; disqualify candidates violating hard constraints; require complete cards and a viability matrix in the saved brief and user delivery when multiple materially different options are viable; require evidence instead of fabricated alternatives when only one option is viable; and prevent forced recommendations when no option fits. **Acceptance:** Given (a) two or more viable options, Spec instructions and template require complete cards, Feature-grounded matrix criteria with one symbol per cell, explanations for partial/failed fit, and the complete comparison in the response; (b) a candidate violating a hard constraint, it cannot be treated as viable or recommended; (c) only one viable option, evidence explains excluded alternatives without a fake matrix; and (d) no viable option, Spec requests the minimum decision. Existing choice and validation gates remain intact. **TDD/characterization:** No behavioral test runner applies to Markdown instructions. Before the change, manually trace the current multi-option, single-option, hard-constraint, and no-fit scenarios and record where the contract is absent or insufficient; after the change, walk those same scenarios against command, guideline, template, and a representative delivery shape. Preserve the current Spec flow and template sections not superseded by this contract. **Gate:** Manual scenario review, internal links and examples check, consistency across command/guideline/template, and diff review; no automated suite or CI gate is configured. **Dependencies:** none.

- **T003-02 — Persist Code status and handoff in one execution record while preserving approved scope.** **Requirements:** S003-01, S003-02, S003-03, S003-04, S003-06. **Precondition:** T003-01 is complete; the existing Code contract, workflow ownership rules, and feature/bug artifacts are reviewed. **Scope:** Update `skills/sdd-lite/commands/code.md`, `skills/sdd-lite/commands/bug.md` where needed for the new artifact lifecycle, `skills/sdd-lite/guidelines/workflow.md` and applicable quality guidance, `skills/sdd-lite/templates/plan.md` and `skills/sdd-lite/templates/bug.md` to remove mutable completion checkboxes, add `skills/sdd-lite/templates/execution.md`, and update `skills/sdd-lite/SKILL.md` routing/flow artifact descriptions. Before editing, trace existing Code behavior for one feature task, one bug task, a Review correction, failed checks, and task-affecting divergence; preserve one-ID-per-execution intent and established scope protections. ## Risks and final verification

The main integration risk is inconsistent ownership or artifact counts across the command, shared workflow guidance, templates, Skill routing, README, and docs page. After all tasks, review the full diff and trace one feature task, one bug task, one Review correction, a pending-to-resumed attempt, and the multi-option/single-option/no-fit Spec paths across those sources. There is no application runtime, data migration, automated test runner, or CI gate; verification is manual documentation and procedure review.

Every Spec requirement is covered: S003-07 through S003-09 by T003-01; S003-01 through S003-04 and S003-06 by T003-02; S003-05 and S003-06 by T003-03; and workflow-wide artifact/documentation alignment under S003-06 by T003-04. Dependencies follow the record contract before Review consumes it, then documentation reflects both. Every task maps to a specified outcome.

Before Code, check that every Spec requirement appears in at least one task and every task delivers an identifiable requirement. Record only real gaps or dependencies between increments.

Code records task state and evidence only in the workflow folder's `execution.md`. Before starting a dependent task, verify predecessor acceptance, changed files, and applicable checks from the execution record and repository; the status alone is insufficient.
