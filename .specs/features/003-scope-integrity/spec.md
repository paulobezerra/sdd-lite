# SPEC — Scope integrity and execution traceability across SDD stages

**ID:** 003-scope-integrity · **Status:** proposed · **Date:** 2026-10-21

**User validation for Plan:** pending. After an explicit statement, record it here with the user's supplied name and the date obtained from the OS, without changing requirements or decisions. The technical decision below is not validation.

## Problem, baseline, and goal

The validated Feature now prioritizes a Spec decision-quality gap: recommendations must follow Feature outcomes and constraints, and users need complete options and a viability matrix when there are multiple viable approaches. The Feature also records execution-traceability gaps. Current instructions confirm that the four-file feature flow is `feature.md`, `spec.md`, `plan.md`, and `review.md`; Code changes only a Plan checkbox, reports test commands/results in the session, and must stop after one ID. A failed gate leaves the item open, but there is no durable status with evidence or resumption details. `workflow.md` also says Code may record a task-affecting decision in Plan, while `code.md` permits only checkbox changes. The README and documentation page describe checkbox-only Code output.

The goal is to preserve approved inputs, make Code's completed or pending state and evidence durable, continue work that remains within the approved task, and let the next Code execution detect pending work. Review must verify completion claims against the criteria, code, diff, and applicable checks. Code needs one dedicated execution artifact so its work and handoff do not require modifying Plan, Review, Feature, Spec, or Bug.

## Scope and constraints

- **Included:** Clarify stage edit boundaries and handling of upstream or implementation divergence; resolve Code's Plan-edit inconsistency; define Code continuation, completion, pending work, and resumption; require Review to independently verify claims; use one dedicated `execution.md` per feature or bug workflow folder for all Code IDs in that folder; strengthen Spec so real multi-option decisions require complete option cards and a viability matrix, show the comparison to the user, and align recommendations with the validated Feature's constraints and priorities.
- **Out of scope:** Implementing the workflow changes in this Spec; changing the Feature/Bug → Code → Review flow; adding a routine approval stage; treating status or checkbox as proof; permitting Code to edit Plan, Review, Feature, Spec, or Bug to record progress.
- **Constraints:** Preserve the lightweight purpose and immutable approved scope. `execution.md` is the only SDD artifact Code may create or edit. Review continues to record audit results in `review.md`, Plan remains the task contract, and Feature/Spec/Bug remain immutable during Code. This adds one file per feature or bug folder. No app runtime, database, or test runner exists; the implementation changes Markdown instructions/templates and aligned README/docs.

### Execution record decision

**Selected approach — dedicated `execution.md`:** One file per feature or bug folder, with append-only entries keyed by Code ID. Code's only SDD artifact write target is this file; it does not edit Feature, Spec, Plan, Bug, or Review.

- **Affected components:** Workflow and quality/review guidance; Code, Plan, and Review commands; execution template; Plan and Bug templates to remove mutable completion checkboxes; `SKILL.md`; README and docs; project-context file-count descriptions.
- **Estimated code impact:** moderate.
- **Fit to Feature:** Meets persistent status, evidence, handoff, resumption, and stage-isolation outcomes for feature tasks, bug tasks, and Review corrections.
- **Benefits:** Gives Code a single owned artifact, preserves stage ownership, and keeps attempts traceable without copying accepted task criteria.
- **Costs and risks:** Adds one artifact per feature/bug folder and updates file-count and discovery conventions. Entries may duplicate information if they copy approved criteria instead of referencing IDs.
- **Constraints or conditions:** `execution.md` is Code's only SDD write target. Other stages may read it; Review records audit results only in `review.md`. Entries reference approved IDs, do not revise contracts, and exclude secrets or sensitive command output.
- **Evidence:** The user's explicit isolation requirement; current write/checklist restrictions in `skills/sdd-lite/commands/code.md`, `skills/sdd-lite/templates/plan.md`, and `skills/sdd-lite/guidelines/workflow.md`.

**Rejected approach:** Store Code status in Plan and Review. It would violate the user's hard requirement that Code use a dedicated artifact and not alter files owned by other stages. It is not a viable option under the validated Feature, so it is not presented as a competing viable choice or ranked in a current viability matrix.

**Why no current comparison matrix is present:** The prior brief compared the two approaches before the Feature was revised to make Code's artifact isolation an explicit hard constraint. Under the validated Feature, the Plan/Review approach is infeasible; the already selected dedicated record is the only viable approach. This follows the Feature's requirement not to fabricate viable options or matrix cells.

## Technical solution

**Technical decision:** On 2026-10-21, Paulo Bezerra selected one `execution.md` per workflow folder: `.specs/features/NNN-name/execution.md` for feature tasks and corrections, and `.specs/bugs/NNN-name/execution.md` for bug tasks. Every Code ID gets an append-only execution entry. Code may create/update only the corresponding `execution.md` among SDD artifacts; normal source-code and test changes within the approved task remain in scope. Code must not change Feature, Spec, Plan, Bug, or Review. Replace mutable checklist completion marks in Plan and Bug with stable task definitions; execution status lives only in `execution.md`.

**Cross-cutting Spec decision quality — highest feature priority:** Update `commands/spec.md` to extract the validated Feature's outcomes, scope boundaries, hard constraints, priorities, and explicit preferences before assessing solutions. A candidate that violates a hard constraint is not a viable option and cannot be recommended. If two or more materially different options satisfy the constraints, the saved decision brief must contain full template-compliant option cards and a viability matrix before asking the user to choose. Cards cover approach, affected components, estimated impact, fit to Feature outcomes/requirements, benefits, costs and risks, conditions, and repository or authoritative evidence. Matrix columns are viable options; rows are relevant, decision-distinguishing criteria grounded in the Feature; each cell has exactly one symbol. Cards explain every ⚠ or ✗. The user-facing delivery presents the complete cards and matrix, not only a file link.

The recommendation must satisfy all hard constraints and explicit preferences, name the Feature criteria that drive the choice, and explain accepted tradeoffs. If no approach fits, Spec must not force a recommendation; it asks the minimum question needed to resolve the conflict. It must not rank options by symbol count. Before delivery, Spec checks that each presented card is a viable candidate, the recommendation answers the user's request, and the recommendation does not optimize implementation convenience at the expense of the Feature.

If only one approach is viable, Spec records the evidence and why relevant alternatives fail the verified constraints, without fabricating option cards or a matrix. The current execution-record decision is in that case: the user made isolation of Code writes a hard constraint, so editing Plan/Review during Code is infeasible; the user already selected `execution.md`.

This Spec-process change is independent of where Code execution state is stored. It updates the shared rule in `guidelines/specification.md`, the requested-stage procedure in `commands/spec.md`, and the artifact shape in `templates/spec.md`, following the project's instruction to keep shared rules in guidelines and stage-specific steps in their command. README/docs are updated only where their description of Spec choices or delivery needs alignment. This is the single evident approach under the repository's composition convention; it does not need a fabricated architecture comparison.

**Single evident implementation for Spec decision quality:**

- **Affected components:** `skills/sdd-lite/commands/spec.md`, `skills/sdd-lite/guidelines/specification.md`, `skills/sdd-lite/templates/spec.md`, and README/docs only where their Spec behavior descriptions need alignment.
- **Estimated code impact:** moderate.
- **Fit to Feature:** Directly delivers S003-07 through S003-09: complete comparisons where real alternatives exist, recommendations that respect Feature constraints, and choices visible in the response.
- **Benefits:** Places the shared decision rule, stage procedure, and artifact shape in their canonical locations so all agents can follow them from repository files.
- **Costs and risks:** Adds an explicit recommendation check and fuller delivery requirements. Real tradeoffs may produce longer responses; the single-viable-solution rule keeps other cases proportionate.
- **Constraints or conditions:** Do not create fake alternatives or matrices. Feature is authoritative for user outcomes and hard constraints; repository evidence establishes feasibility. Keep the behavior agent-independent.
- **Evidence:** `.specs/implementation.md` requires shared rules in guidelines, stage procedures in their command, artifact shape in templates, and repository-file usability. Existing option-card and matrix structures are in `skills/sdd-lite/templates/spec.md`.

An entry records the Code ID and type, linked requirement/task/finding IDs, attempt date, `PENDING` or `SUCCESS`, changed paths, checks actually run with result, and any relevant limitation. If work remains pending, it records the blocker or failed condition, remaining work, and the precise next step, including user input needed when applicable. A Code invocation starts by writing or appending a `PENDING` entry, then autonomously completes all work within scope. It records `SUCCESS` only after every acceptance criterion and applicable gate is satisfied; otherwise it leaves `PENDING`. Attempts are appended so the prior handoff is not lost.

Before starting a different Code ID, Code reads `execution.md`. If the most recent entry for any earlier ID is `PENDING`, it resumes that ID and does not start a later ID. A completed ID may be revisited only for an explicitly requested correction or a Review finding. Code does not mark Plan or Bug checkboxes. Review reads execution entries but independently checks criteria, diff, code, and applicable checks; its conclusion and findings remain in `review.md`.

When an upstream contract conflicts with implementation or a requested change would exceed the approved scope, Code does not resolve it by editing an upstream artifact. It leaves the execution `PENDING`, records the observed divergence, impact, remaining work, and the decision or validation needed, then waits for that input. Routine implementation details that do not change product behavior or approved scope may be resolved within Code and recorded in the execution entry.

**Reason for the decision:** The dedicated record directly satisfies the user's requirement that Code progress be durable and that Code not modify artifacts owned by other stages. The added file is justified by coverage across feature tasks, bug tasks, and Review corrections; the entry references approved IDs rather than copying their contracts to limit duplication. The separate Spec-process change directly addresses the demonstrated failure: a recommendation favored editing Plan and Review for convenience even though this conflicted with the Feature and explicit user intent.

**Accepted tradeoffs:** One extra file per feature or bug workflow; execution history is separate from task definitions; Plan/Bug checkboxes no longer indicate completion; Review remains the independent acceptance audit. Spec adds a visible comparison when real choices exist, while one-solution cases require evidence rather than invented options. No Feature deviation is introduced: the validated Feature explicitly includes both the decision-quality behavior and a persistent execution record when simpler changes cannot meet the handoff need.

## Contracts, data, and security

- **Artifact paths:** One `execution.md` in each `.specs/features/NNN-name/` or `.specs/bugs/NNN-name/` folder. It is the only SDD artifact written by Code.
- **Entry identity:** Code ID plus kind (`feature task`, `bug task`, or `Review correction`) and linked requirement/task/finding ID. Do not duplicate approved acceptance text.
- **State:** `PENDING` from the start of an attempt until all criteria and applicable gates pass; `SUCCESS` only after they pass. Append later attempts rather than overwriting prior entries. No entry means Code has not started that ID.
- **Checks:** Record command or manual procedure, result, and relevant environment/limit. Never represent an unrun check as passed. A nonzero or blocked applicable gate leaves the entry pending.
- **Permissions and preservation:** Code may change source, tests, and `execution.md` within its approved task; among SDD artifacts it may not edit Feature, Spec, Plan, Bug, or Review. Review may read execution records but writes findings only to `review.md`.
- **Sensitive data:** Record concise, sanitized command/result details and paths. Never copy secrets, tokens, real environment values, or sensitive logs into execution entries.
- No application route, API payload, database, authentication, or migration is affected.
- **Spec decision contract:** The Feature is the source for user outcomes and constraints. Repository evidence establishes feasibility and baseline; it cannot override explicit user intent. Matrix symbols communicate fit criterion by criterion and are not scores.

## Acceptance and verification criteria

- **Success status:** Given all task acceptance criteria and applicable gates pass, when Code finishes the ID, then the latest entry is `SUCCESS`, lists actual checks/results and changed paths, and approved SDD source artifacts are unchanged. Verify by instruction/template consistency review and representative diff inspection.
- **Pending status:** Given a relevant test fails or the environment blocks an applicable check, when Code cannot complete within the invocation, then the entry remains `PENDING` and names the reason, remaining work, and next step; no later ID starts. Verify with procedure scenarios and a review of the required execution-entry fields.
- **Out-of-scope divergence:** Given implementation requires a product or scope decision, when Code encounters the divergence, then it preserves approved artifacts, records the decision needed and impact in `execution.md`, and waits for the response. Verify that command instructions prohibit upstream edits and describe the pending handoff.
- **Review:** Given an execution entry claims `SUCCESS`, when Review audits, then it checks the claim against Feature/Spec/Plan or Bug, code, diff, and applicable checks and records audit results in `review.md`. Verify the Review procedure and template against false/missing evidence scenarios.
- **Integration/compatibility:** Feature and bug file inventories, templates, SKILL routing, README, and docs all identify the new artifact and its ownership; Code and Review correction flows resolve the correct path. Verify links, examples, file trees, and terminology across those files.
- **Spec multi-option decision:** Given a Feature with at least two materially viable approaches, when Spec is run, then complete option cards and a symbol-only viability matrix are saved and presented to the user before requesting a choice. Verify card fields, matrix cells, evidence for partial/failed criteria, and delivery text.
- **Spec recommendation boundaries:** Given a candidate that is easier to implement but violates a hard Feature constraint, when Spec evaluates options, then that candidate is not presented as a viable recommendation. If no candidate satisfies all hard constraints, Spec requests the minimum clarification. Given a single viable approach, Spec explains with evidence why alternatives fail and does not fabricate a matrix. Verify with these three documented decision scenarios.

**Applicable gate:** Manual documentation and guideline consistency, link and example checks, and diff review. No repository test runner or CI gate is configured; no automated tests are specified for this documentation-only change.
