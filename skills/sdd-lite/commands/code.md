# SDD Lite · Code

Execute **one ID** per invocation: a feature task (`TNNN-XX` in `plan.md`), a bug task (`BNNN-XX` in `bug.md`), or one correction identified in `review.md`. The ID prefix tells the flow (`T` → `.specs/features/…`, `B` → `.specs/bugs/…`); a Review correction uses the folder containing that `review.md`. Read `.specs/project-context.md` (if missing, suggest `$sdd-lite init`), [workflow](../guidelines/workflow.md), and [quality](../guidelines/quality.md). Read `.specs/implementation.md` for project conventions. The Spec defines the target; code and tests show the actual baseline.

Before starting, apply the [context isolation rule](../guidelines/workflow.md#recommended-isolation-clean-context-for-each-execution). If a previous execution's context is still present, briefly warn about the quality and traceability risk and recommend clearing the context, either here or in a new conversation. Do not block the user; if they explicitly insist on continuing with accumulated context, proceed and state in the delivery that they authorized the exception. Reconstruct state from versioned artifacts and the actual repository. End after the selected ID, even if blocked; another ID requires clean context or a new warning.

## 1. Resolve the execution and fix its scope

1. Resolve the workflow folder and execution record: `.specs/features/NNN-name/execution.md` for a feature task or correction, `.specs/bugs/NNN-name/execution.md` for a bug task or correction. If the user's requested ID differs from an ID whose latest entry is `PENDING` in that folder, resume the pending ID first; do not start later work. A resumed invocation is a new appended attempt for that same ID. Otherwise use the supplied ID; without one, choose the first open and eligible Plan task or first ready Review correction. State the ID, linked requirement/task/finding IDs, and observable expected result.
2. **Feature:** read Feature, Spec, Plan, and Review when present; before the first Code ID, verify Plan validation. **Bug:** read `bug.md` (and `review.md` when present) and verify its validation before first Code. Do not require validation again for each iteration. Check task order and dependencies; for every prerequisite, verify completion from the execution record and confirm the diff, implementation, and applicable checks support it. A status alone is insufficient. If the requested task is not ready, explain the dependency and do not implement it. Compare the approved contract with code, tests, and affected consumers. If work requires a product or scope decision, preserve approved artifacts and record the needed decision and impact in `execution.md`; wait for the user's response. Resolve routine implementation questions directly.
3. Inspect workspace state and relevant diff to separate pre-existing changes. Identify all paths needed for the slice. Before implementation, append a new attempt to `execution.md` with status `PENDING`, linked IDs, current changed paths (or `none`), checks not yet run, limits, and remaining work/next step. Do not copy acceptance text into the record.

## 2. Implement and gather evidence

1. For new or corrected behavior, first write a test that fails **for the expected reason**. Before refactoring existing behavior, characterize the contract that must remain. Make the smallest change that turns the test green, then refactor with tests green. For documentation-only or configuration-only work, use a check capable of detecting a real error when possible; do not invent a test that merely confirms the written text.
2. Follow the conventions in `.specs/implementation.md`; if the task requires breaking one, record the conflict and impact in the active `execution.md` attempt and wait for the user's decision. Complete the vertical slice, including affected consumers. Preserve external contracts and existing data unless an approved decision says otherwise. Use a new migration when an applied schema must remain compatible; database reset, destructive rollback, or volume cleanup requires explicit authorization and target verification. When risk depends on integration, check that boundary: API/authorization, persistence/transaction, client application, or deployment configuration.
3. Run focused checks during the work. If a check fails, distinguish a task regression, a pre-existing failure, and an environment block with evidence. Fix issues within this ID; do not expand into unrelated refactoring. Continue all recoverable in-scope work during this invocation. Stop only for an external blocker or a product/scope decision, and record remaining work and the next step.

## 3. Verify the task

1. Compare the result with every acceptance criterion and linked requirement/finding. Check success, relevant failure, preservation, and affected contracts/documents. Run the task's focused checks and applicable quality gates. Follow project-context commands, environment, and authorization limits. In the active attempt, record actual changed paths, commands or manual procedures, results, environment limits, and remaining work.
2. Among SDD artifacts, Code may create or edit **only** the workflow folder's `execution.md`. Do not edit Feature, Spec, Plan, Bug, or Review to record progress, decisions, or completion. Update the active attempt's status to `SUCCESS` only after every acceptance criterion and applicable gate passes. Otherwise leave it `PENDING` and state the blocker, remaining work, and next step. Append later invocations as new attempts; never overwrite earlier attempts. For a Review correction, implement the finding and record it in the same folder's execution record; Review later verifies the correction in `review.md`.
3. End the response with the matching `SUCCESS` or `PENDING` status and the same outcome as the latest entry. For `PENDING`, say whether work continues within scope or stopped for a blocker/decision, and identify remaining work and next step. Do not start another ID or Review in this invocation.
