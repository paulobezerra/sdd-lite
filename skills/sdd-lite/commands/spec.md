# SDD Lite · Spec

Turn a `feature.md` into a chosen and verifiable technical solution. Read `.specs/project-context.md` (if missing, suggest `$sdd-lite init`), [workflow](../guidelines/workflow.md), [specification](../guidelines/specification.md), and the [template](../templates/spec.md). Read `.specs/implementation.md` for the project's conventions. One invocation performs Spec only; it does not start Plan or Code.

Before starting, apply the [context isolation rule](../guidelines/workflow.md#recommended-isolation-clean-context-for-each-execution). If a previous execution's context is still present, briefly warn about the quality and traceability risk and recommend clearing the context, either here or in a new conversation. Do not block the user; if they explicitly insist on continuing with accumulated context, proceed and state in the delivery that they authorized the exception. Reconstruct state from versioned artifacts and the actual repository. End after Spec; any technical choice needed belongs to this execution.

## 1. Check the baseline and input quality

1. Identify the feature by ID or context. If candidates cannot be distinguished, ask for the ID. Check explicit user validation for Spec in `feature.md`, with name and OS date. If missing, apply the [entry rule](../guidelines/workflow.md#entry-premise-explicit-validation-of-the-previous-step). Check the recorded branch; for a Feature predating the branch rule, establish the branch and complete this metadata in `feature.md` without changing decisions. Read the Feature and inspect directly affected files, contracts, tests, data, and consumers. Distinguish verified current behavior, assumptions, and desired behavior; record differences between a historical Spec and actual code.
2. Find gaps that prevent a decision: actor, permission, initial state, action, result, failure, data to preserve, or scope boundary. If the Feature needs more precision, state exactly what is missing and why it affects the solution; ask only for essential product choices before proposing architecture. Do not fill silence with an invented contract.

## 2. Technical decision

1. Extract the Feature's desired outcomes, scope boundaries, hard constraints, priorities, and explicit preferences before comparing solutions. Separate hard constraints from preferences and other decision drivers. Start from assumptions checked in the Feature and code, distinguishing verified facts, assumptions, and product wishes. Exclude any candidate that violates a hard constraint. For a meaningful tradeoff among the remaining candidates, present **two or three materially different viable options by default**, including retaining the current design when it meets the Feature; add another only when it adds a genuine choice. Do not fabricate alternatives to meet a count. A recommendation must respect all hard constraints and explicit preferences and name the decisive Feature criteria and accepted tradeoffs. If no candidate fits the hard constraints and explicit preferences, do not force a recommendation; ask for the minimum decision needed. If only one solution is viable, explain with evidence why relevant alternatives fail and do not ask the user to choose.
2. Before asking the user to choose, create or update `spec.md` as a **decision brief** with status `decision pending`. Include the verified baseline, extracted constraints and drivers, complete option cards, a viability matrix, an evidence-based recommendation, and the exact decision requested. Use the card format in the Spec template. Each card states approach, affected components, estimated code impact (**low, moderate, or high**), fit to Feature requirements, concrete benefits, costs and risks, constraints or conditions, and supporting repository or authoritative evidence. Explain every partial or failed fit in the card. For a single viable solution, record evidence for it and why relevant alternatives fail; do not invent cards or a matrix.
3. For multiple viable options, compare options as columns and relevant, decision-distinguishing Feature criteria as rows. Use the broad catalog in [specification](../guidelines/specification.md) as a checklist, selecting only applicable criteria and adding Feature-specific drivers as needed. Every matrix cell contains exactly one symbol: **✓** meets the criterion, **✗** does not meet it, or **⚠** partial or conditional fit. Put the legend beside the matrix. Do not put prose, scores, or totals in cells, and do not rank options by counting symbols. The cards provide the evidence and explain every ⚠ and ✗. Link criteria to Feature requirement IDs where practical.
4. For multiple viable options, save the complete cards and matrix in `spec.md`, then present those same complete cards and matrix in the user-facing delivery before asking the user to choose or adjust an option. State an explicit, nonbinding recommendation and name its decisive Feature criteria and accepted tradeoffs; the recommendation is not approval. If the choice was already expressed in this conversation, use it without asking again. When awaiting a choice, stop after saving and presenting the decision brief; do not proceed to Plan or Code or present unchosen design details as a final contract. For one clearly evident solution, present its evidence and why relevant alternatives fail in both the brief and delivery, then proceed without asking the user to choose. If no candidate fits, explain the conflict and ask only for the decision needed to resolve it; do not recommend an incompatible option.

## 3. Specify and check

1. After the user's choice or adjustment, update that same `spec.md`: record the choice, accepted tradeoffs, and date, then complete the technical contract. Do not treat the choice as approval of a Feature deviation or as Spec validation. For a clearly evident single solution, complete the Spec with its evidence-based justification and do not attribute a choice to the user. Assign stable requirement IDs. For each relevant behavior, describe initial state, action, and observable result, including success, invalid input, denied access, and partial failure where relevant. Define contracts, invariants, data transitions, migration, and affected consumers at the level needed for acceptance.
2. Link every requirement to a verification method proportional to risk. Check consistency with the Feature, stack, `.specs/implementation.md`, current code, and existing contracts. **Do not change `feature.md`**, including when a later decision contradicts it. In that case, record the original Feature statement, the divergent decision, and its impact in the Spec; ask the user to explicitly validate the deviation and treat it as current only after recording that validation in the Spec. Resolve routine details in the Spec. Do not mark implementation progress here.
3. Leave Spec validation for Plan pending in `spec.md` until the user explicitly states it; the earlier technical decision does not count. After the statement, record it only in that field with the user's name and the OS date, without rewriting requirements or decisions. Deliver the link, recorded decision, and any essential open question. Stop before Plan or Code.
