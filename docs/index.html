Get started in three steps

The skill is project-agnostic. Everything about your project is generated by init and lives in your repository.

1 · Install

Once, globally

Run the command above. The skill is available to every project and every agent that supports skills.

2 · Init

$sdd-lite init

In an empty project it interviews you; in an existing one it analyzes the code. It writes the project context and the implementation conventions.

3 · Work

Feature or bug

Use feature for new capabilities and bug for pinpoint defects. Start each step with a clean context.

Syntax: $sdd-lite <command> [ID or free text] in Codex, /sdd-lite <command> … in Claude Code and similar agents. With no command, the skill lists the options.

Two flows, one rule set

Pick the flow by the nature of the work. code and review serve both: the ID prefix (T… feature task, B… bug task) tells them where to work.

Feature

New capability or behavior change

feature→spec→plan→code→review

Four artifacts: feature, spec, plan, review. You validate Feature, Spec and Plan explicitly before the next step. Spec compares real technical alternatives and waits for your choice.

Bug

Pinpoint defect, local fix

bug→code→review

Two artifacts: bug and review. One validation instead of three. bug triages first and redirects to the feature flow when the problem is not truly pinpoint, so it saves tokens without hiding real design work.

Bug qualifies only if existing behavior contradicts a clear expectation, the cause is local, and the fix needs no contract change, migration, or design choice.

What lands in your repository

The skill stays global and generic. Your project owns its knowledge in versioned, human-readable files.

.specs/
├─ project-context.md   # what the project is
├─ implementation.md    # how code is written here
├─ features/
│  └─ 001-name/
│     ├─ feature.md
│     ├─ spec.md
│     ├─ plan.md        # task checklist
│     └─ review.md
└─ bugs/
   └─ 001-name/
      ├─ bug.md         # diagnosis + tasks
      └─ review.md

project-context.md

Purpose, stack, structure, verified commands, authorization limits, current state and open questions. Read by every command.

implementation.md

Conventions on boundaries, contracts, security, data and testing. Each rule is observed (with evidence), decided (confirmed by you) or assumption; review enforces only the first two. Read by spec, code, bug and review.

Rules that keep it honest

Explicit validation

Feature → Spec → Plan → Code (or Bug → Code) need your statement, recorded in the artifact with your name and the OS date. A checkbox or silence is not approval.

Immutable inputs

Spec never rewrites Feature, Plan never rewrites Spec, Code only ticks checkboxes, Review changes none of them. Divergences are recorded in the current artifact and await your approval.

Clean context per step

Each command starts from the artifacts and the real repository, not conversation memory. If context is dirty, you get a warning, never a block.

Evidence, not claims

Only checks actually run count. Code proves one task; the first review runs the full suite and gates. An unrun test is never reported as passed.

Never blocks you

Want to bend a rule? The agent explains the risk and the recommended path; if you insist, it proceeds and records the authorized exception.

Safe by default

No commit, push, deploy or destructive operation without your request. No secrets in artifacts. No subagents or loops without authorization.

FAQ

Does it work with agents other than Codex?

Yes. The rules live in plain Markdown that any agent can read. If an agent has no native command syntax, say “run sdd-lite <command>”.

Do I have to run init?

It is strongly recommended: other commands read the generated files. Without them they warn you and proceed only if you insist.

Bug or feature, how do I choose?

Run bug when something that should work is wrong and the fix is small and local. It triages for you and redirects to feature when a product decision, contract change or migration is involved.

Where do project-specific rules go?

In .specs/implementation.md, via init. Never inside a feature artifact, and never in the skill itself.
